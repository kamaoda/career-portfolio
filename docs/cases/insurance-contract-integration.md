# 複雑な保険契約変更に対応する外部連携バッチの設計・実装

## 概要 {#overview}

損害保険関連システムで、保険契約の変更に応じて外部システムとのデータ連携を制御するバッチ処理の設計・開発を担当しました。

対象の業務では、契約情報が有効日順に届くとは限らず、過去の日付に適用される変更が後から届くこともありました。また、外部システムからの応答によって次に必要な処理が変わるため、入力と応答の組み合わせを個別に列挙する方法では設計が複雑になり、方針を定められない状況でした。

そこで私は、**DBに保持した契約情報と外部連携の結果をもとに、その時点で必要な処理をSQLで導出する**設計方針を提案しました。方針を約1週間で整理してPowerPointにまとめ、関係者に説明しました。この方針が採用され、中核となるデータモデル・SQL・Spring BatchのJavaコードを自ら設計・実装しました。

さらに、JUnit・DbUnit・LocalStack・簡易モックを組み合わせ、**複数年にわたる日次バッチの処理と最終的なDB状態をローカルで自動検証する仕組み**を構築しました。

## 背景と課題：入力パターンの列挙では設計が進まなかった {#background}

保険契約に関する情報は、必ずしも新規契約、変更、取消という順序で届くわけではなく、有効日の古い順に届くとも限りません。例えば、すでに別の変更が反映された契約に対して、さらに過去の日付を有効日とする変更が後から届くことがあります。また、新規契約の情報よりも先に、その契約の取消情報が届くこともありました。

このような情報の到着順序と契約上の時系列の食い違いに加え、現在は外部システムへの連携対象外となっている契約について、過去の期間に対する追加処理が必要になる場合もありました。

さらに、外部システムへの要求は一度で完結するとは限らず、**返ってきた結果に応じて、次に何を要求するかを判断する**必要がありました。

当初は、契約変更や外部応答の組み合わせを個別に列挙し、それぞれに対応する処理を定義する方法で設計を進めようとしていました。しかし、情報の到着順序や過去の処理状況まで考慮するほど検討対象が増え、複数の担当者が約2か月にわたって検討しても設計方針が定まらない状況でした。

## 設計方針：DBに記録された情報から必要な処理を導出する {#design}

私が提案したのは、過去に届いた変更の順番を各機能が個別に追跡するのではなく、**DBに蓄積された情報を基準に、その時点で必要な処理を判断する**方式です。

判断材料を、主に次の3つに整理しました。

- **業務上の事実**：契約の対象、適用期間、変更を反映した契約情報など
- **外部連携の結果**：外部システムからの応答によって確認できた処理結果や状態
- **処理実績**：データ取得や処理完了の状況など、追加処理の要否を判断するための情報

これらをSQLで照合し、その時点で必要な処理を導出する構成としました。外部システムから応答が返ってきたら結果をDBに反映し、次回の実行時には更新後の情報から改めて判断します。

この考え方をPowerPointの資料にまとめ、関係者に説明しました。資料では、方針が抽象論で終わらないよう、次の内容まで具体化しました。

- **契約状態の整理**：外部連携の判断に必要な契約状態を実質4種類に整理し、状態遷移図で表現
- **データモデルと処理フロー**：DBで管理する情報と、それを利用した処理の流れを整理し、前述の契約状態はDBに保持した情報から導出できることを示した
- **バッチジョブの構成**：障害時のリカバリを考慮したジョブネットの構成と、各Stepの具体的な処理内容を説明
- **具体的な入力データによる動作例**：入力データの例を用意し、各段階での状態変化と処理の流れを順に示して、提案した方式の具体的な動作を説明

その後、提案した方式が設計方針として採用されました。

ポイントは、状態遷移のすべてをJavaの条件分岐や単一のステータス値で表現しようとしなかったことです。業務上の事実から導出できる判断はSQLで都度行い、外部システムの応答によって初めて確定する状態は明示的に管理しました。

例えば、**外部システムからのデータ取得が完了し、結果が0件だった場合と、取得処理自体がまだ完了していない場合は区別する必要があります**。両者を区別できるようにし、データが存在しないという理由だけで不要な再処理を繰り返さない仕組みにしました。

なお、この方式は、順不同で到着した契約情報の整合性や、過去の契約履歴の正しさまで保証するものではありません。**契約情報が適切にDBへ反映された後、外部連携で何を実行すべきか**を判断するための設計です。

## 実装：複雑な抽出条件はSQL、処理単位への集約はJava {#implementation}

実装にはSpring Batchを使用し、主な処理を次のように分担しました。

1. **Readerで実行するSQL**：契約情報・外部連携の結果・処理実績を照合し、追加処理が必要な対象を抽出する。
2. **Javaでの集約処理**：抽出結果を後続処理で扱いやすい単位にまとめる。
3. **後続のStep**：判断結果に基づき、外部連携に必要なデータを出力する。

SQLでは、契約が現在有効かどうかという単純な判定だけでなく、**過去の期間に対する処理が必要かどうか**も考慮しました。

毎回DB上の情報から処理対象を導出することで、当初の設計方法で課題となっていた、入力パターンごとに専用の条件分岐を増やし続ける状況を回避しました。

中核となるSQLは自分で記述しました。Javaについても、集約処理を含むSpring BatchのReader・Processor・Writerの主要部分を自ら実装しています。

チームは私をリーダーとする約4名体制でした。私は複雑な業務判断を伴う中核処理の設計・実装を担当し、メンバーには、連携対象としてDBに登録されたレコードを外部連携用のファイルに出力する処理などを担当してもらいました。メンバーが実装した機能のレビューも行いました。

また、関連する他チームの設計レビューも担当しました。

## ローカル自動テスト：複数年分の日次処理を連続実行 {#automated-testing}

このシステムでは、一つの契約変更に伴う外部連携が複数日にまたがって進む場合があります。そのため、1回分のバッチが正常終了したことを確認するだけでは、一連の処理が正しく完了するかを検証できません。

そこで、**JUnitからSpring Batchを処理日付ごとに繰り返し起動し、複数年分の日次処理を連続実行したうえで、最終的なDB状態を自動検証する**仕組みを作りました。

具体的には、Excelで初期データと期待結果を作成し、自作したVBAでDbUnit用のXMLを生成しました。DbUnitでテスト前のデータを投入し、JUnitから処理日付を進めながらジョブを連続実行した後、**最終的なDBの内容を期待結果のXMLと照合**する方式です。

S3相当のファイル入出力にはLocalStackを使用し、外部システムからの応答はJavaで作成した簡易モックで代替しました。

クラウド上のバッチ実行基盤を毎回起動せずに済むため、**長期間にわたる業務ロジックをローカルで繰り返し検証**できました。また、後続のAWS環境でのシナリオテストに先立ち、不具合を発見・修正することにも役立ちました。

## 成果 {#results}

- **難航していた設計方針を具体化し、実装へつなげた。** 約2か月間方針が定まらなかった設計に対し、代替方針を約1週間で整理・資料化しました。提案した方式が採用され、中核となるデータモデル・SQL・Javaの設計と実装を担当しました。
- **複雑な契約変更に対する処理判断を整理した。** 入力順序ごとの個別分岐ではなく、DBに蓄積された情報を基準に必要な処理を判断する構成としました。
- **複数年の日次処理を自動検証できるようにした。** JUnit・DbUnitなどを組み合わせ、複数日にまたがる業務シナリオを、最終的なDB状態まで実装段階からローカルで確認できる仕組みを整えました。
- **後工程の前に不具合を発見・修正できた。** 外部システムへの要求処理に関する不具合を、実装段階のローカル検証で発見・修正しました。その後のAWS環境でのシナリオテストでは、担当範囲で新たな不具合は検出されませんでした。

## 振り返り {#reflection}

この取り組みで重視したのは、**入力パターンの数だけ処理を増やすのではなく、業務上何が分かっていれば次の処理を判断できるかを整理すること**でした。

その考え方をデータモデルとSQLに落とし込み、主要部分を自ら実装しました。さらに、日付をまたぐ複雑な処理についても、外部連携をモックやLocalStackで代替することで、複数年にわたるシナリオをローカルで繰り返し検証できるようにしました。

**業務の複雑さをデータと処理の責務に分解し、設計から実装、検証まで一貫して取り組んだ経験**です。
