# 5年分の日次バッチ検証の効率化

> **検証の目的に立ち返り、確認対象・実行方法・証跡作成の手順を見直した事例**

## 概要 {#overview}

業務システムのシナリオテストで、約5年分の日次バッチ処理を検証する必要がありました。

当初はAWSマネジメントコンソールからバッチを1日ずつ手動で起動し、終了確認や検証資料の作成を繰り返していました。この方法では、1日あたり約2日分の処理しか進まない状況でした。

私は途中からテストリーダーを引き継ぎ、検証方針と作業手順を見直しました。すべての日付のバッチ実行は維持しつつ、詳細な業務検証は約50か所のイベント日に集中する方針とし、AWS CLIによる実行スクリプトとExcelの検証テンプレートを作成しました。

その結果、**2名体制で、スクリプトの開発も含め約3週間で検証を完了しました。**

## 背景：なぜ5年分の日次処理が必要だったのか {#background}

対象システムでは、業務データの状態が長期間にわたって変化するため、一連の処理が正しく行われることをシナリオテストで確認する必要がありました。通常の処理だけでなく、過去日付に遡っての変更や、複数年にまたがる状態変化も検証対象となっていました。

また、日次処理には過去の実行状態に依存する部分があり、途中の日付を省略すると検証条件が変わってしまう可能性がありました。

そのため、**バッチ実行日は省略せず、5年分を日付順に連続して実行する必要がありました**。一方、業務データの状態変化など、**詳細な結果確認が必要なイベントは、テスト仕様の段階であらかじめ約50か所に定義**されていました。

## 課題：実行と確認のすべてを人手で繰り返していた {#challenges}

従来は、AWSコンソールからバッチを起動し、作業者が画面を繰り返し更新して完了を待っていました。終了後にDBの状態を確認し、スクリーンショットなどの証跡を作成してから、次の日付へ進む方法でした。業務イベントがない日についても、DBの状態が変わっていないことを毎回確認していました。

また、個々の起動画面を保存する方法では、対象日付のバッチを漏れなく実行できたかを一覧で把握しにくいという課題もありました。

## 実施した改善 {#improvements}

### 1. 検証方針を「全日の実行確認」と「イベント時の詳細確認」に分離

検証の目的を整理し、次の方針へ変更しました。

- **すべての日付のバッチの実行は維持。** 日次処理の連続性を維持するため。
- **すべての日付の実行状況の確認も維持。** ただし、AWSコンソール画面のスクリーンショットではなく、Spring Batchの実行管理DB（JobRepository）に記録されたジョブ実行履歴・終了状態・実行パラメータなどを利用。
- **業務データの詳細な検証は、定義済みの約50か所のイベント日に集中。** 業務データの状態や関連する処理結果を、その時点の期待結果と照合。

これは「5年分のうち約50日だけ実行した」という意味ではありません。**実行する範囲は減らさず、人間が詳細確認する箇所を整理した**ものです。

### 2. AWS CLIとシェルスクリプトで反復操作を自動化

処理基準日を引数として受け取るシェルスクリプトを、約1日で作成しました。AWS CLIを使い、S3への入力データ配置、Fargate上のバッチ起動、処理完了までの待機といった一連の操作をまとめました。

通常日は所定のテスト用入力ファイルを使用し、特定のイベントでは個別に用意したテストデータを使用しました。イベント固有のテストデータは、事前に手作業で準備しました。

また、Excelのオートフィルで日付を連続生成し、各日付に対応したスクリプト実行コマンドを関数で作成しました。これを使って日付順に処理を進めることで、作業者がブラウザに張り付き、終了まで画面更新を繰り返す必要をなくしました。

### 3. Excelの検証テンプレートで実績値と期待値を照合

検証資料のひな形も私が作成しました。処理基準日などからSQLを組み立てるExcel関数を用意し、担当者がDBに対してSQLを実行して、その結果をExcelに貼り付けられるようにしました。

テンプレートでは、あらかじめ用意した期待値と、貼り付けた実績値をVLOOKUPなどの関数で照合しました。値を取得できない場合や期待値と異なる場合は赤、正常な場合は緑になるよう、条件付き書式を設定しました。Spring Batchの実行結果も同様に、正常終了かどうかを一覧で確認できるようにしました。

期待値の作成と実績値の反映は主に担当メンバーが行い、私は**期待値そのものが業務仕様に照らして妥当か**、また**照合結果に問題がないか**をレビューしました。色がすべて緑でも期待値が誤っていれば適切な検証にはならないため、期待値のレビューを重視しました。

### 4. バッチ実行中に次の検証準備を進められるようにした

従来は「ジョブを起動 → 終了を待つ → 検証資料を作る → 次のジョブを起動」という逐次作業でした。

改善後は、バッチを自動実行している間に、担当者が次のイベントの検証資料や期待値を準備できるようになりました。結果が得られたらSQLの照会結果などを貼り付け、差異を確認する流れに変わりました。**短縮したのはバッチ自体の処理時間ではなく、人間の待機時間と繰り返し作業**です。

## 成果 {#results}

- **約5年間の日次バッチ検証を約3週間で完了。** スクリプト作成、検証資料の準備、関連システムの担当会社との調整・待機を含む期間です。
- **必要な日次実行を維持したまま、詳細な確認作業を集約。** 定義済みの約50か所のイベント日に集中できました。
- **実行待ちを作業時間から切り離した。** 担当者はバッチ実行中に検証準備を進められるようになりました。
- **実行状況の確認方法を改善。** Spring Batchの管理情報と対象日付を照合し、画面上の操作記録だけに依存せず、実行状況を一覧で確認できるようにしました。

## 担当範囲 {#responsibilities}

このシナリオテストは、**私（リーダー）と担当メンバー1名の2名体制**で進めました。

- **私：** 検証方針の見直し、シェルスクリプトの作成、SQL生成・照合機能を持つExcelテンプレートの設計と実装、検証方法の共有、期待値と検証結果のレビュー
- **担当メンバー：** 日々の実行・確認、シナリオごとの期待値作成、SQLの実行と結果の貼り付け、検証資料の作成

約3週間での完了は、**メンバーを含むチーム全体の成果**です。

## 振り返り {#reflection}

この取り組みで重視したのは、既存の手順をそのまま速くすることではなく、**「何を保証するための検証なのか」を整理すること**でした。

5年分のバッチを実行する必要性は変わりませんでした。一方、毎日すべてのDB項目を人手で確認したり、作業者がバッチの終了を待ち続けたりする必要はありませんでした。また、大量のスクリーンショットを残すだけでは、実行日付の網羅性も十分に確認できませんでした。

Spring Batchがもともと持つ実行管理情報と、AWS CLI・シェルスクリプト・SQL・Excelを組み合わせ、**必要な確認を維持しつつ、人間が判断すべき部分に時間を使える検証手順**へ改めました。
