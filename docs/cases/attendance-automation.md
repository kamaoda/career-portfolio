# 既存の勤怠管理SaaSを活用した残業・有給計算の自動化

> **新規アプリの開発を求められたが、既存システムと業務ルールを見直し、約50人分の月次集計を一括処理できる仕組みを実現した事例**

## 概要 {#overview}

前職の社内業務で、約50人分の残業時間・残業代・有給休暇の月次集計を改善しました。

従来は社員ごとに勤怠データを取得し、Excelでの計算・手動補正・ダブルチェック・転記を繰り返していました。担当者は他業務と並行して進めていたため、集計完了まで少なくとも2週間以上を要していました。

会社からの当初の要求は、勤怠管理アプリの新規開発でした。しかし、既に導入されていた勤怠管理SaaSには未活用の機能が多くあることが調査で判明し、**新規開発を行わずに、既存SaaSの活用・業務ルールの見直し・Excelによる計算の自動化**で解決する方針を提案しました。

その結果、全社員分を一括計算できるようになり、従来の2名によるダブルチェック体制から、**担当者1名が入力締め後に基本1時間未満で集計を完了できる運用**へ変更しました。

## 背景と課題：手作業の集計が限界に達していた {#background}

従来の勤怠集計は、役員が他業務の合間や休日に作業することで維持されていました。役員の負担軽減のため別の社員へ業務を移管したところ、手動計算と確認作業が非常に多く、継続的な運用が難しいことが問題になりました。

社員数も約50人に達しており、これ以上増えると従来の方法では対応できない状況でした。

会社では既に勤怠管理SaaSを導入していましたが、社内独自の勤務ルールや例外的な勤怠に対応するため、標準の集計機能を十分に活用できていませんでした。

そのため、会社からは新しい勤怠管理アプリの開発が求められました。

### 従来の業務フロー

勤怠管理SaaSから社員ごとに1か月分のCSVを出力し、既存のExcelに貼り付けて集計していました。

Excelには勤務時間を時間帯別に分類する機能がありましたが、有給消化時間などは社員が入力した勤務区分やメモ欄を確認しながら、担当者が日付ごとに判断・計算する必要がありました。

さらに、**別の担当者が全日付について有給消化時間などの計算結果を確認するダブルチェック**も行っていました。

これらを全社員分繰り返した後、結果を別ファイルへ集約していました。

### 集計処理以外の課題

- **入力ルールが統一されていない：** 勤務区分やメモ欄の使い方が社員によって異なり、機械的な判定が難しい状態でした。
- **勤務条件に応じた判断が必要：** 社員ごとに所定労働時間が異なるほか、テレワークと出社で遅刻・早退の扱いが異なるなど、社内独自の計算ルールがありました。また、健康診断など、一部の勤怠については人間による個別の判断が必要でした。
- **既存Excelの計算に制約がある：** 固定的な休憩時間を前提としており、分割休憩や勤務途中の中抜けを正しく扱えないケースがありました。

単にExcelの計算式を増やすだけでなく、入力データの管理方法から見直す必要がありました。

## 解決方針：新規開発より先に、既存SaaSで解決できる範囲を調査 {#approach}

勤怠管理アプリを新規開発する場合、勤怠計算以外にも、ログイン機能やアクセス権限の管理、勤怠入力画面などの開発・運用が必要になります。

一方、既存SaaSには勤怠情報の記録やCSV出力などの機能が既に備わっていました。

そこで私は、**新規開発を前提にせず、既存SaaSの機能でどこまで解決できるかを先に調査する**方針を提案しました。

メンバーにSaaSの機能調査や提供会社への仕様確認を任せ、会社から挙がっていた課題に対して既存機能をどう活用できるか検討してもらいました。

調査結果をレビューしたところ、勤務区分や勤務場所の設定、全社員分のCSV一括出力、複数回の休憩時間の記録など、活用できる機能があることが分かりました。

これを踏まえ、次の方針をまとめました。

1. **既存SaaSを勤怠情報の入力・管理に使用する。**
2. **機械的に処理できるよう、勤務区分や入力ルールを見直す。**
3. **社内独自の計算処理はExcelで補完する。**
4. **一意に判断できない例外処理は、人間が確認・補正する。**

メンバーに経営層向けの提案資料を作成・発表してもらい、新規アプリを開発せずに進める方針について了承を得ました。

## 実施した改善 {#improvements}

### 1. 勤務区分と入力ルールを再設計し、曖昧な入力を減らす

従来の勤務区分には曖昧な項目（例：「その他」など）があり、実際の勤務状況を正確に表現できないケースがありました。また、同じ勤務状況でも社員によって入力方法が異なり、メモ欄の自由記述を読まなければ判断できないこともありました。

そこで勤務区分を整理し、例外的な勤務状況の入力方法を明確にしました。

例えば、勤務場所によって遅刻・早退の扱いが異なるため、SaaSに備わっていた勤務場所の設定機能を活用しました。

勤務区分と勤務場所を別々の情報として管理することで、勤務区分を必要以上に増やさず、Excel側で適用する計算ルールを切り替えられるようにしました。

社員向けには入力方法を説明するフローチャートを作成し、質問があった内容はQ&Aとして追加しました。

**計算処理で曖昧な情報を推測するのではなく、入力段階で必要な情報を整理すること**を重視しました。

### 2. 全社員分を一括計算するExcelを設計

既存SaaSには全社員分の勤怠データをCSVで一括出力する機能がありましたが、従来は社員別に計算する運用だったため活用されていませんでした。

そこで、全社員分のCSVを一度に取り込み、社員ごとの勤務条件に応じて自動計算するExcelを作成しました。

Excelは、**入力・計算処理・出力の3つに役割を分離**しました。

| 区分 | 主な内容 |
| --- | --- |
| 入力 | 全社員分の勤怠CSV、社員別の勤務条件、有給休暇残高、残業代計算用の時間単価 |
| 計算処理 | 勤務区分・勤務場所・勤務時間・休憩時間などに応じた残業・有給計算 |
| 出力 | 社員別の残業時間・残業代・有給休暇残高 |

計算処理はExcel関数だけで実装しました。

所定時間外労働・法定時間外労働・深夜労働などを区別し、社員ごとの勤務条件や社内ルールを反映できるようにしました。

休憩時間についても、SaaSから複数回の休憩開始・終了時刻を取得し、Excel側で計算することで、従来の固定的な休憩時間の前提を見直しました。

また、**有給休暇残高の出力形式を翌月の入力形式に揃え、コピー＆ペーストで引き継げる構成**としました。

Excelの全体設計は私が担当し、具体的な計算処理の実装は主にメンバーが担当しました。

複雑な計算でも依存関係を追いやすいよう、データの参照方向をできるだけ統一するなど、実装方針を共有して開発を進めました。

### 3. 人間の判断が必要な例外を、自動化せず明示する

健康診断など、勤務していない時間の理由によって有給消化時間が変わるケースは、勤怠データだけでは一意に判断できませんでした。

こうしたケースまで無理に自動化するのではなく、人間が判断した値を入力できる仕組みにしました。

手入力が必要なセルは黄色で表示し、未対応の項目がある場合は出力シートにも警告を表示しました。担当者が値を入力すると、該当セルの表示が緑色に変わるようにしました。

これにより、**全社員の全日付を人間が詳細確認するのではなく、判断が必要な箇所を優先的に確認できる**ようになりました。

## 検証：過去約1年分の実データによる新旧比較 {#verification}

計算処理の実装後は、Excel関数のレビューと、あらかじめ用意した勤務パターンによるテストを行いました。

ただし、勤務区分・勤務場所・休憩時間・社員ごとの勤務条件などの組み合わせが多く、**開発者が想定したテストケースだけで十分な網羅性を確保するのは難しい**と判断しました。

そこで、過去約1年分の実際の勤怠データを新しい入力形式に変換し、従来方式と新方式の計算結果を比較しました。

差異が発生した場合は、従来方式を無条件に正解とせず、どちらに問題があるのかを調査しました。

その過程で、次のような問題が見つかりました。

- **把握できていなかった業務ルール：** 客先ごとに異なる所定勤務時間について、特定の社員には例外的かつ暗黙的な計算ルールが適用されており、新しいExcelに反映する必要がありました。
- **従来方式の計算上の問題：** 分割休憩や勤務途中の中抜けを、従来のExcelでは適切に計算できていないケースがありました。

これらの差異を調査し、必要に応じて計算仕様や実装を修正しました。

**想定したテストケースによる検証と、実際の業務データによる新旧比較を組み合わせることで、開発時に把握できていなかった業務ルールや既存の計算上の問題を発見できました。**

## 本番移行と運用定着 {#migration}

Excelの実装には約1か月、移行準備を含めると全体で約2か月を要しました。

本番移行に向けて、SaaSの設定変更、新しい入力要領の社内周知、移行手順、リハーサルなどを計画しました。

メンバーに移行計画や手順書の作成を任せ、私は内容のレビューや指導を担当しました。

社員向けには新しい入力ルールを説明する資料を、集計担当者向けにはExcelの操作や例外処理の手順書を用意しました。

また、社員への周知では、変更日や重要事項が見落とされないよう、メールのタイトルや本文の視認性にも配慮しました。

本番切り替えは大きな問題なく完了し、社員からの問い合わせもほとんどありませんでした。

**本番移行後も約3か月間は従来方式との並行運用を継続**し、計算結果に差異が生じた場合は原因を確認しました。

その後も日常的な改修はほとんど発生せず、安定して運用されました。ただし、計算式の修正が必要になったことはあり、不具合が一切なかったわけではありません。

## 成果 {#results}

| 項目 | 改善前 | 改善後 |
| --- | --- | --- |
| 対象人数 | 約50人 | 約50人 |
| 集計方法 | 社員ごとに個別計算・確認 | 全社員分を一括計算 |
| 手動作業 | 日付ごとの判断・手計算と全日分のダブルチェック | 自動判定できない例外のみ補正 |
| 担当体制 | 2名によるダブルチェック | 1名で集計 |
| 集計完了まで | 少なくとも2週間以上 | 入力締め後、基本1時間未満 |
| システム構成 | 既存SaaSと社員別Excelによる手動集計 | 既存SaaSと一括計算用Excel |

**数値についての注記：** 改善前の「2週間以上」は他業務と並行した集計完了までの経過期間であり、実作業時間ではありません。改善後の「1時間未満」は入力締め後の集計時間です。測定条件が異なるため、工数削減率は算出していません。

今回の改善により、社員数に応じて繰り返し発生していた手作業を減らし、担当者1名で月次集計を完結できる運用へ変更しました。

また、新規アプリの開発を回避できたため、独自アプリの認証・アカウント管理などを新たに開発・運用する必要もありませんでした。

## 担当範囲 {#responsibilities}

今回の取り組みは、私と担当メンバーが役割を分担し、業務部門とも協力して進めました。

**私が主に担当したこと**

- 既存SaaSの活用による代替方針の立案
- メンバーによる機能調査・課題分析・経営層向け提案の指導とレビュー
- 勤務区分や例外処理など、業務ルールの整理
- Excelの全体設計と実装方針の決定
- 計算式のレビュー、検証方針の策定
- 本番移行計画・運用手順のレビュー

**担当メンバーが主に担当したこと**

- 既存SaaSの機能調査、提供元への問い合わせ
- 経営層向けの提案資料作成・発表
- Excel関数による詳細な計算処理の実装
- テストデータの作成・検証
- 本番移行計画や操作手順書の作成

集計業務の運用変更や確認体制の見直しは、業務部門の判断・協力のもとで進めました。

## 振り返り {#reflection}

今回の取り組みで重視したのは、会社から提示された「新しい勤怠管理アプリを開発する」という手段ではなく、**「手作業の勤怠計算から担当者を解放する」という本来の目的**でした。

既存SaaSには活用できる機能が数多くありましたが、会社独自の勤務ルールをすべて標準機能だけで扱うことも困難でした。

そこで、既存SaaSで対応できる部分はそのまま活用し、必要に応じて業務ルールを見直し、不足する計算だけをExcelで補完しました。

また、すべての例外を自動判定することにはこだわらず、人間が判断すべき部分を明確に残しました。

**新しいシステムを開発すること自体を目的とせず、既存の仕組み・業務ルール・人間の判断を適切に組み合わせることで、必要な機能を実現する。**

今回の事例は、その考え方を実践した取り組みです。
